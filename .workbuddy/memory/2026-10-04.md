# 2026-10-04

## 排查「指令已送达但客户端无响应」

### 现场证据
用户发 `{"name":"run_workflow","parameter":{},"other":{},"from":["server"],"to":["5a13a4fe"]}`，
网页端提示已连接，客户端零响应。

逐步排查：
1. `GET /api/clients` 确认 `5a13a4fe` **在线**（当时叫 `ComfyUI-3738`，sender）
2. 翻服务端日志 → `指令「run_workflow」已转发给 1 个客户端：['ComfyUI-3738']`
   **服务端这一段是通的，指令确实投递出去了**
3. 查该客户端 UA → `Mozilla/5.0 (Windows NT 10.0...) Chrome`
   → **不是 ComfyUI 节点（无头 UA），是浏览器里的页面**（油猴脚本之类）
4. 结论：客户端连了、也收到了，但**没实现指令处理，也没回 command_result**，
   所以网页端看起来「石沉大海」。

### 改进（让下次排查不用猜）
- `command_result` 区分两种：`awaiting_ack:true` = 只是「已送达」，
  没有该字段 = 客户端**真的回执了**。前端日志也据此分色：
  投递提示标 `out`（灰青）+ "等待回执…"，真回执标 `exec`（紫）。
- 服务端维护 `_pending_cmds`，日志会打 `↳ 等待客户端回执` / `✓ 客户端已回执「x」：detail`。
- 新增内置指令 `whoami`：客户端回它就能确认通道是否连通、回执带 id/名字。
- 新增 `tools/probe_command.py`：直接探测某个客户端「收没收到 / 回没回执」。

### 探针自身的 bug（写测试时踩到）
`recv(ws, want)` 原来只收一条、不匹配就丢弃 —— 但连接上**先来的是 `clients` 广播**，
于是把真正的 `command_result` 读漏了，误报「服务端没回执」。
**教训：WebSocket 收消息必须循环跳过不匹配的，而不是读一条就返回。**
修法：`recv` 加 pred 参数，循环直到 type 匹配且满足条件。

### 验证
前端桩补「投递提示 vs 客户端回执」等 4 项，前端扩到 105 项；五套共 236 项全通过。
